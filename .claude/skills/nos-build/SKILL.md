# NOS 활동 만들기 오케스트레이터

## 왜 이렇게 가볍게 하나
이전 저장소(`C:\Users\mrdoo\Documents\nos_game_project`)는 태스크마다 구현 에이전트 + 태스크 검토 + 원고 검토 + 시각 검토 + 아트 검토를 돌렸고, 수정 루프가 최대 5회였다. 사용자 판단: **너무 느리다.** 그래서 이 하네스는
- 구현을 **메인 세션이 직접** 하는 것이 기본이다(맥락을 다시 설명하는 비용이 없다).
- 검토는 **단계가 끝날 때 한 번씩**, 에이전트 둘(원고·사료 / 플레이)만 쓴다.
- 지적을 고치는 라운드는 **1회**. 사소한 것은 모아서 한 번에.

**실행 모드:** 메인 세션 직접 구현 + 서브에이전트 위임(큰 덩어리 구현 1명, 단계 끝 검토 2명). 에이전트끼리 대화할 필요가 없어 지속형 에이전트·워크플로는 쓰지 않는다.

## 0. 시작할 때 확인
1. `docs/superpowers/specs/`의 설계 문서와 `docs/superpowers/plans/`의 계획을 읽는다. 계획이 없으면 만들지 말고 `superpowers:writing-plans`로 먼저 계획을 쓰자고 사용자에게 말한다.
2. `work/ledger/<id>/progress.md`(장부)가 있으면 마지막 완료 단계 다음부터 이어 간다. "○○ 단계만 다시"면 그 단계만 다시 하고 장부에 사유를 남긴다. 없으면 새로 만든다. 첫 줄: `# 장부 — 계획: <계획 파일>`.
3. `nos-gamedev`를 읽어 외부 스킬을 어떻게 쓸지 확인한다.

## 1. 단계

| 단계 | 하는 일 | 쓰는 스킬 | 끝날 때 검토 |
|---|---|---|---|
| A 준비 | Vite+Phaser+TS 뼈대, 고정 화면(480×360, 정수 배율), 명령어(`typecheck`·`test`·`check:script`·`shots`·`e2e`) | `phaser-core` | 없음(`nos-check` 통과만) |
| B 프로토타입 | 회색 상자 대륙 끌어 맞추기(②③). 원고 없음 | `prototype-fast`, `input-systems`, `game-feel` | **사용자가 직접 해 본다** → 계속/수정 결정 |
| C 공통 부품 | UI 장면(대화·선택지·안내 띠), 원고 파서·쪽 나눔 검사 | `game-ui-ux`, `dialogue-systems`, `visual-novel` | 플레이 검토 |
| D 원고 | 사실 확인 → 원고 → 한국어 점검 → 사용자 확인 | `nos-script` | 원고·사료 검토 |
| E 그림 | STYLE.md → 견본 → 판정 → 대량 | `nos-art`, `create-game-assets` | 플레이 검토(그림 일관성 포함) |
| F 나머지 장면 | ④⑤⑥ 장면, 정리 페이지 | — | 원고·사료 검토 + 플레이 검토 |
| G 마무리 | 끝까지 플레이 e2e, 스크린샷, 사용자 플레이테스트 안내 | `nos-check` | 플레이 검토(전체) |

단계 안에서는 계획의 태스크 순서를 따른다. 태스크마다 `superpowers:test-driven-development`로 만들고(판정·쪽 나눔·파서 같은 논리), 화면은 스크린샷으로 확인한다. 태스크가 끝나면 `nos-check`를 돌리고 커밋한다.

## 2. 누구에게 맡기나

| 역할 | 누가 | 모델 | 언제 |
|---|---|---|---|
| 구현 | 메인 세션 | — | 기본 |
| 큰 덩어리 구현 | `nos-implementer` | sonnet | 한 태스크가 크고 독립적일 때(예: 원고 파서+검사 전체). 한 번에 한 명(같은 작업 트리) |
| 원고·사료 검토 | `nos-content-reviewer` | sonnet (깊은 사실 확인이 막히면 `model: opus`로 올림) | 단계 D·F 끝 |
| 플레이 검토 | `nos-play-reviewer` | sonnet | 단계 C·E·F·G 끝 |
| 한국어 점검 | `humanize-korean:humanize-monolith` | — | 원고를 쓰거나 고친 뒤(고치지 말고 바꿀 문장 목록만) |

`model`은 항상 명시한다(빠뜨리면 세션 모델을 물려받는다). 검토 두 개가 함께 걸리는 단계는 한 메시지에서 병렬로 부른다.

## 3. 검토 지적 처리
- 검토 결과는 메인이 `work/ledger/<id>/<단계>_<검토자>.md`에 옮겨 적는다(에이전트는 파일을 쓰지 않는다).
- Critical·Important는 메인이 한 번에 고치고, 고친 항목만 같은 검토자에게 한 번 다시 보인다. **그 뒤에도 남으면 장부에 남기고 사용자에게 알린다(더 돌리지 않는다).**
- Minor는 장부의 `Minor:` 목록에 모았다가 단계 G에서 한 번에 처리하거나 버린다.

## 4. 멈추고 사용자에게 묻는 경우 (이것뿐)
- 단계 B 끝(프로토타입을 직접 해 볼 차례).
- 원고 초안 완성(단계 D), STYLE.md와 그림 견본(단계 E): 인상과 말투는 사용자가 정한다.
- 되돌릴 수 없는 일: push, 배포, 저장소 밖 파일 변경, 요금이 드는 대량 그림 생성(견본 수·예상 호출 수를 먼저 알린다).
- 설계와 계획이 부딪혀 모든 선택이 추측일 때.
그 밖의 모호함은 판단해서 장부에 `판단:`으로 남기고 계속한다.

## 5. 장부 (`work/ledger/<id>/progress.md`)
한 줄씩: `단계 X 태스크 N: 완료 (커밋 abc1234)`, `판단: …`, `Minor: …`, `검토 C 플레이: 수정 2건 → 고침`. `work/`는 git에 넣지 않는다(장부 `ledger/`, 그림 생성 원본 `art-runs/`, 내려받은 자료 `data/`, 디버그 화면·로그 `debug/`).

## 6. 오류 처리
- 서브에이전트 실패는 한 번 다시 시도한다. 사용량 한도·권한 거부는 다시 시도하지 않고 장부에 남긴 뒤 사용자에게 알린다(한도는 풀리는 시각도).
- 멈춘 에이전트의 판단을 추측해 채우지 않는다. 메인이 직접 확인한 사실만 장부에 적는다.
- 그림 생성 키(`OPENAI_API_KEY`)가 없으면 그림 단계를 건너뛰고 회색 상자로 F·G를 먼저 끝낸다(설계 8절). 사용자에게 알린다.

## 7. 폴더 구조와 다음 활동(플로지스톤 등)

```
src/engine/        모든 게임 공통: 화면·배율, UI 장면(대화창·선택지·안내 띠), 입력, 끌어 맞추기, 디버그
src/engine/script/ 원고 읽기·쪽 나누기·줄바꿈·검사
src/rpg/           고전 RPG 틀: 걷기(Walker), 칸 길찾기(grid), 정리 창(SummaryScene)
activities/<id>/   한 주제의 모든 것
  index.html         게임 페이지(주소 /<id>/ — Vite 플러그인이 스스로 찾는다, 설정 고칠 것 없음)
  script.md sources.md *.json towns/ art/
  game/              이 주제만의 장면·로직. main.ts(시작), anchors.ts(원고 앵커 목록, check:script가 읽음)
  tools/             이 주제 전용 생성 도구(지도·그림)
  tests/unit/ tests/e2e/   이 주제 전용 테스트(vitest·playwright가 스스로 찾는다)
scripts/ tests/    공통 도구·공통 테스트(e2e helpers는 tests/e2e/helpers.ts)
work/              git 밖 작업 폴더(5절)
```

- 주제 코드에서 공통 부품은 별칭으로 가져온다: `@engine/...`, `@rpg/...`. 같은 주제 안은 상대 경로.
- 새 주제는 같은 단계표를 쓴다. `activities/<새 id>/`에 위 구조를 만들고(대륙이동설의 `index.html`·`game/main.ts`·`game/anchors.ts`를 본보기로), `src/engine`·`src/rpg`는 고치지 않고 쓴다.
- 대륙이동설의 마을·제목·항해 장면(`activities/continental-drift/game/scenes/TownScene.ts` 등)은 아직 주제 전용이다. 두 번째 주제를 설계할 때 두 예시를 놓고 마을·진행 순서·지도 이동을 데이터로 바꿔 `src/rpg`로 옮긴다(계획: `docs/superpowers/plans/2026-10-31-folder-structure.md`).
- 공통 부품(`src/`)을 바꾸면 모든 주제가 깨지지 않는지 `nos-check --e2e`로 확인한다.

## 테스트 시나리오
- 정상: "계획대로 만들어" → 장부 생성 → A(뼈대, `nos-check` 통과, 커밋) → B 프로토타입 → 사용자에게 "직접 해 보세요" 안내하고 멈춤 → 사용자 "계속" → C … → G → 사용자 플레이테스트 안내.
- 오류: 단계 D 원고·사료 검토에서 Critical 1건("해저 줄무늬로 바로 받아들여졌다"는 신화) → 메인이 원고 수정 → 같은 검토자 재검토 통과 → 장부 기록 → E로.
- 오류: 단계 E에서 키 없음 → 장부에 `판단: 그림 보류` → F·G를 회색 상자로 끝냄 → 사용자에게 키 넣기 안내.
